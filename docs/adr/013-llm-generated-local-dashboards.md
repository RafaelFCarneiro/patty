# ADR-013: LLM-generated, data-less local dashboards over the HTTP API

**Status:** Proposed · **Date:** 2026-06-27 · **Deciders:** Rafael · Opens the **presentation layer** for
Phase 3/4. Strategic direction (multi-phase); each phase ships its own design + PR.

## Context

FinTrack is AI-first: chat (MCP tools/agents/skills) is the primary way the user interacts, and that stays.
Real-world dogfooding surfaced two complementary needs:

1. **Better chat presentation.** Prompts/preferences that bring data back in a more relevant, readable shape
   (the user already maintains an `AGENTS.md` with statement-formatting rules, icons, and a hard
   *"never use cache/snapshot — always query FinTrack in real time"* rule).
2. **A visual UI to grasp the financial situation** — and crucially, a UI **generated by the agent to the
   user's own perspective**, not a pre-determined fixed layout. Different users (and the same user in a
   different financial moment) care about different cuts; an LLM-built UI adapts where a hard-coded one cannot.

A first dashboard was produced via the tool (`dashboard_financeiro.html`), and it works — but it bakes the
**entire dataset inline** as JS constants (`spending`, `accountTransactions`, `accounts`,
`recurringExpenses`, `installmentExpenses`). That is a stale snapshot frozen into the file: it violates the
project's real-time-data principle (the same rule `AGENTS.md` states for chat), and it bakes private financial
data into a shareable artifact. The presentation was good; the data embedding is the thing to eliminate.

The goal: **the agent authors the presentation (the shell); the data stays live behind the API.**

## Decision

1. **Chat (MCP/agents/skills) remains the primary entry and interaction point.** Dashboards complement it.
2. **The FinTrack HTTP server serves both the data API and the generated dashboards, same-origin.** The HTTP
   surface (already secondary to MCP) hosts the read API under `/api` and the generated dashboards under a
   `/ui` surface. Same origin ⇒ dashboards `fetch()` live data with no CORS friction, and the server is the
   natural home to store/list dashboards.
   - **Dashboards are stored *content*, not a bundled asset — so they're replaceable at runtime.** A dashboard is
     a self-contained HTML string persisted by name (a `dashboards` entity: `name`, `html`, `updated_at`). The
     agent writes/overrides it through a normal MCP write (`save_dashboard(name, html)` — an upsert), and
     `GET /ui/:name` returns whatever is *currently* stored. Overriding the UI is therefore just re-upserting
     under the same name: no rebuild, restart, or redeploy — the new shell shows on the next reload. **The shipped
     template is only a default seed, never a fixed/compiled UI.** (This is the deliberate reason the UI is HTML
     content the server hands back, not a front-end build artifact — generated, per-user, runtime-replaceable UIs
     would be hard if it were the latter.) Name-keyed storage also allows several dashboards (`overview`, `cards`,
     `month-review`) overridden independently, and `updated_at`/version history enables "revert my dashboard."
     Serve with no-cache headers so a regenerated dashboard isn't masked by a stale browser copy.
3. **Generated dashboards are data-less HTML shells.** The agent produces layout/charts/styling only; the page
   fetches from the documented endpoints on load and renders. **No data, no secrets, ever embedded** in the
   file — the non-negotiable rule. This makes dashboards always-fresh (real-time principle) and privacy-safe
   (a shared file leaks nothing; data lives behind the local API).
4. **FinTrack publishes its REST contract for discovery.** An **OpenAPI** document is exposed at a discoverable
   URL and as an **MCP resource**, so the UI-building agent generates correct `fetch` calls against the real
   contract instead of guessing shapes.
5. **A UI-building skill encodes the guardrails** (fetch-only — never inline data/secrets; use the OpenAPI
   contract; allowed CDN chart libs; theming/accessibility; the real-time rule) and scaffolds from a **baseline
   data-less template** FinTrack ships (the cleaned-up version of the draft).
6. **REST-first.** The existing read endpoints (`aggregate_spending`, `get_spending_summary`,
   `search_transactions`, balances, `list_*`) are the dashboard data sources; add read endpoints as gaps
   appear. **GraphQL is deferred** to a later ADR if UI data-shape needs outgrow REST.

## Options Considered

### Option A — Data baked into the generated HTML (the draft's current approach) — rejected
| Dimension | Assessment |
|---|---|
| Freshness | **Stale** — a snapshot frozen at generation time |
| Privacy | **Leaks** — private data embedded in a shareable file |
| Adaptivity | High (agent builds layout) |
| Effort | Lowest |

**Cons:** violates the real-time-data principle (cf. `AGENTS.md`); private-data leak; every refresh needs a
re-generation. Rejected.

### Option B — Ship a pre-built fixed UI with the app — rejected
**Pros:** deterministic, no per-render agent involvement.
**Cons:** the entire value here is per-user / per-situation tailoring; a fixed UI can't anticipate every
perspective. Contradicts the AI-first thesis.

### Option C — LLM-generated data-less shell over same-origin REST + OpenAPI contract + UI skill — **chosen**
| Dimension | Assessment |
|---|---|
| Freshness | Always live (fetch on load) |
| Privacy | No data in the file — safe to share |
| Adaptivity | Full — agent tailors the view to the user |
| Cost | A contract-discovery mechanism + http-mode runtime + trusting the no-data rule (mitigated below) |

**Sub-decisions:** serving = **same-origin server route** (chosen) over `file://`+CORS (null-origin friction);
data layer = **REST-first + OpenAPI** (chosen) over GraphQL-now (large new surface; deferred to its own ADR).

## Trade-off Analysis

The tension is **adaptivity + freshness + privacy** vs. **the machinery to make a generated UI safe and
correct**. Option C pays three bounded costs — publishing a contract, requiring http mode for the UI, and
relying on the agent to follow the no-data rule — and buys a UI that is always live, leaks nothing, and adapts
to each user. The reliance on the agent is mitigated structurally: same-origin serving removes the incentive to
inline data "to avoid CORS"; the OpenAPI contract gives the agent the real shapes; and the UI skill makes
fetch-only the default path. A generated dashboard can still be ugly or wrong, but it is cheap to regenerate and
**data correctness is guaranteed by the API, not the HTML** — the failure mode is cosmetic, never wrong numbers
or stale data.

## Consequences

- **Enabling layer (new):** an OpenAPI document published at a route **and** as an MCP resource; a `/ui` serving
  surface on the http server with dashboard storage + listing; a baseline data-less dashboard template; a
  UI-building skill. **http mode becomes required for the dashboard feature** (chat/MCP stdio default — ADR-007 —
  is unaffected).
- **Existing read tools become data sources:** `aggregate_spending`, `get_spending_summary`,
  `search_transactions`, `get_account_balances`, `list_*`. Read-endpoint gaps (e.g. recurring + installment
  projections the draft showed) get filled as the template/skill need them.
- **Reprioritizes Phase 3:** this groundwork precedes `save_view`/`find_correlations`/budgets, which then become
  **data the dashboards render** (a saved view → a dashboard panel; correlations/budgets → cards).
- **Security/privacy (local single-user):** CORS scoped to localhost; the no-inline-data rule doubles as a
  privacy guarantee; the skill forbids embedding secrets/tokens. Auth stays out of scope (local-first) — revisit
  via a separate ADR only if multi-user/remote ever lands.
- **Chat presentation (need #1)** is addressed in parallel by MCP prompts/preferences (the `AGENTS.md` rules are
  a strong starting point) — tracked separately from this UI ADR.

## Action Items (phased — each phase = its own design + PR)

**Phase A — contract + serving groundwork**
1. [ ] Publish an OpenAPI spec for the REST API at a route (e.g. `/api/openapi.json`) and expose it as an MCP
   resource for discovery.
2. [ ] Serve a `/ui` surface from the http server (same-origin with `/api`). Add a `dashboards` entity (`name`,
   `html`, `updated_at`) + repo; `save_dashboard(name, html)` (MCP write, upsert) and `list_dashboards` tools;
   `GET /ui/:name` returns the currently-stored HTML (`text/html`, no-cache). Override = re-upsert by name (the
   template is only a default seed). Optionally retain version history for "revert my dashboard". Light save-time
   guardrail (skill enforces no inline data/secrets; full HTML sanitization is overkill for a local single-user
   app authoring its own UI).
3. [ ] Document running in http mode for dashboards (and how a chat client points the UI at it).
4. [ ] **REST integration tests (prerequisite).** The HTTP routes are currently covered only via MCP; the
   dashboards consume REST directly, so add HTTP-level integration tests (Fastify `inject` against an in-process
   libSQL DB) for each `/api` route before relying on it as the UI contract. (An existing GitHub issue already
   tracks this gap — reference it from the implementing PR.)

**Phase B — UI generation**
4. [ ] Ship a baseline **data-less** dashboard template (the cleaned-up draft: fetch-on-load, no inline data).
5. [ ] Author the **UI-building skill**: fetch-only guardrails, OpenAPI-contract usage, allowed CDN libs,
   theming/accessibility, the real-time rule.

**Phase C — data coverage + integration**
6. [ ] Fill REST read-endpoint gaps the template/skill require (accounts+balances, recurring, installments, …).
7. [ ] Wire `save_view` as dashboard panels; later, `find_correlations` / budgets as cards.

**Later (separate ADRs):** GraphQL data layer if REST proves insufficient; auth if the threat model changes.
